## 二、背景与判断结论

### 2.1 结论

**需要，但只做一个后台，不做中台。** 在现有 `Admin.tsx` + `AdminController` 上扩三个模块（动作库 / 官方内容 / 配置中心），复用率估算 ≥60%，MVP 约 5–6 人周。

### 2.2 三条硬依据（已核对代码）

| # | 事实 | 后果 |
|---|------|------|
| 1 | 135 条内置动作写在 `sql/fitlog_seed.sql`，形式为 `INSERT IGNORE` | **改已有行不生效**（主键冲突直接跳过），纠错只能手工 `UPDATE` 生产库，无版本、无回滚、无审计 |
| 2 | `exercises` 表无 `status`/`version`/`updated_by`/`redirect_to` 字段 | 归档、合并、影响评估无承载结构，只能写一次性脚本 |
| 3 | 官方内容与运营旋钮无生产路径 | 公告/官方文章/官方模板/帮助页无处可发；10 条配置以裸 KV 存在 `app_settings`，改错即事故 |

补充：主 PRD 11.2 要求审核、下架、注销、导出全部可追溯，但后台账号体系不存在（`users.role` 默认 `user`，靠改它提权会让前台注册链路直通后台）。

### 2.3 不做的代价（估算，需研发校准）

| 项 | 单次成本 | 频次 | 月成本 |
|----|----------|------|--------|
| 内置动作新增/纠错（改 seed.sql → 发版 → 回归） | 1–2 小时 | 20–40 次/月 | 5–10 人日 |
| 官方文章/公告发布（手工 INSERT `posts` + 指定 user_id） | 1–2 小时 | 6–10 次/月 | 1.5–3 人日 |
| 配置调整（手工 UPDATE `app_settings`） | 0.5 小时 + 沟通 | 2–4 次/月 | 0.5–1 人日 |
| **合计** | — | — | **7–14 人日/月** |

后台 MVP 预估 5–6 人周；回收期约 3–4 个月。真正的收益是**把"不敢改"变成"敢改且可撤回"**。

## 三、目标与成功指标

### 3.1 业务目标

| 目标 | 说明 |
|------|------|
| G1 运营独立 | 动作库增改、官方内容发布、配置调整**不依赖研发发版** |
| G2 口径安全 | 影响统计口径的变更**可预判、可回滚、可审计** |
| G3 合规可查 | 账号到人、操作留痕、处置可对外说明 |
| G4 不拖累前台 | 后台故障与重任务**不影响**记录、上传、打卡 |

### 3.2 北极星指标

**动作变更自助交付率** = 无需研发介入即在前台生效的动作变更次数 ÷ 同期全部动作变更次数

- 口径：一次动作发布计 1；批量导入按 1 个批次计 1；回滚计 1。研发介入 = 需改代码或直接操作数据库。
- 目标：**≥90%**（现状估算 ≤20%）。
- 来源：埋点 `adm_exercise_publish.assisted_by_dev`。

### 3.3 成功度量

| 指标 | 口径 | 目标 |
|------|------|------|
| 动作变更交付时长 | 提交 → 前台生效，中位数 | ≤30 分钟 |
| 动作变更事故数 | 导致前台错误/统计异常的变更次数 | 0 次/月 |
| 回滚成功率 | 触发回滚后 5 分钟内恢复的比例 | 100% |
| 官方内容发布周期 | 草稿创建 → 前台可见，中位数 | ≤2 小时 |
| 官方内容月成本 | 官方科目实测账单 | ≤¥10 |
| 官方内容抽查不合格率 | 不合格条数 ÷ 抽查条数 | ≤10% |
| 审核 SLA 达成率 | 高危 15min / 常规 24h 内处理比例 | ≥95% |
| 配置生效时长 | 保存确认 → 全端生效 P95 | ≤60 秒 |
| 测试号数据泄漏 | 测试数据进入看板/名额计数的例数 | 0 |

## 四、名词与术语

| 术语 | 定义 |
|------|------|
| 内置动作 | `exercises.is_builtin=1` 且 `owner_id IS NULL`，全体用户可见可选 |
| 自建动作 | 用户创建（`owner_id=user_id`），仅本人可见（主 PRD FR-22） |
| 敏感字段 | 影响统计口径或历史归属的动作字段：`primary_muscle`、`type` |
| 安全字段 | 别名、说明、要领、媒体、排序权重——直接生效 |
| 生效策略 | 敏感字段修改后的处理方式：**不追溯**（默认，仅新记录）／**全量重算**（历史重算，需审批） |
| 动作版本 | 一次修改的字段快照，含前后值与变更人 |
| 合并重定向 | A 合并到 B 后 A 保留 `redirect_to=B`；历史记录仍归 A，统计与 PR 聚合到 B |
| 官方号 | 系统账号（`users.role='official'`），承载全部官方内容，不可登录、不可关注 |
| 官方内容 | 归属官方号的公告 / 官方文章 / 官方训练模板 / 帮助页 |
| 单人复核 | 默认模式：提交人自查后发布，受 8 项清单 + 冷却 + 抽查约束 |
| 双人复核 | 严格模式：提交人与复核人必须不同 |
| 待抽查队列 | `single_review=1` 的内容队列，用于月度抽查 |
| 配置项 | `app_settings` 中的运营旋钮，按风险分低/中/高 |
| 工单授权 | 处理举报/申诉时临时获得内容查看权，24h 自动失效 |
| 名额 | 主 PRD FR-92 的每日公开内容名额，全站共享 20 条 |
| 测试号 | `users.is_test=1` 的验收账号，数据全链路隔离 |

## 六、方案对比与选型

| 维度 | A 不做后台 | B 扩展现有 Admin（推荐） | C 独立中台 |
|------|------------|--------------------------|------------|
| 实现成本 | 0（隐性 7–14 人日/月） | 中（9–11 人周） | 高（30+ 人周） |
| 口径安全 | 差：无版本无回滚 | 好 | 好但过度 |
| 合规留痕 | 差：无账号体系 | 满足 | 满足 |
| 运营独立性 | 无 | 完整 | 完整 |
| 与 ¥30 成本约束匹配 | 不匹配 | 匹配 | 不匹配 |
| 结论 | 不采用 | **推荐** | 不采用 |

**推荐理由**：现有后台已验证鉴权、分页、日志、UI 骨架（15 接口 / 7 页签），三个新模块与其共享分页、块渲染、媒体引用、审计、角色校验，复用率估算 ≥60%。重写等于把已验证部分再赌一次。

**工作量（估算）**：V1.0 约 2.5–3 人周，V1.1 约 2.5–3 人周，V1.2 约 1.5–2 人周。

## 七、角色与用户故事

### 7.1 角色（一期实际 1 人，模型预留 4 角色）

| 角色 | 一期 | 核心职责 | 可见范围 |
|------|------|----------|----------|
| 超级管理员 | **1 个账号（当前唯一）** | 全部操作，含高风险配置与敏感字段重算 | 全部 |
| 运营 | 0（由超管兼任） | 动作库、官方内容、配置调整 | 除账号管理 |
| 审核员 | 0（由超管兼任） | 审核、举报、申诉初审 | 审核队列/举报/规则库 |

### 9.2 官方内容成本测算（估算）

**单价**（沿用主 PRD 8.5 量级，以供应商报价为准）：标准存储 ¥0.12/GB/月、低频 ¥0.08/GB/月、CDN ¥0.20/GB、转码 ¥0.04/分钟。

**规模假设**：135 个内置动作中 **100 个**配示范视频（长尾用 3 张关键帧图）；单条 **45 秒**、720p / 2.5Mbps ≈ **14MB**；100 用户 × 月 20 次 = **2,000 次播放**。

| 成本项 | 用量 | 单价 | 月成本 |
|--------|------|------|--------|
| 转码（一次性 ¥3.0，摊 12 个月） | 100 条 × 0.75 分钟 = 75 分钟 | ¥0.04/分钟 | ¥0.25 |
| 存储（含封面约 1.6GB，30 天后转低频） | 1.6GB | ¥0.12 / ¥0.08 | ¥0.19 |
| **CDN 流量** | 2,000 × 14MB = **28GB** | ¥0.20/GB | **¥5.60** |
| **合计** | — | — | **≈¥6.0 / 月**（余量 40%） |

### 9.3 三条结论

**结论一：大头是播放流量（93%），不是存储与转码。** 护栏重点应是"监控播放量"，而非"限制上传条数"。

**结论二：100GB 是容量上限，不是可用额度。**

| 情形 | 计算 | 结果 |
|------|------|------|
| 100GB 全按标准存储 | 100 × ¥0.12 | ¥12/月 → **已超 ¥10** |
| 100GB 全按低频 | 100 × ¥0.08 | ¥8/月 → 只剩 ¥2 给流量（≈10GB，不够 2,000 次） |
| 实际用量 ≈1.6GB | 1.6 × ¥0.12 | ¥0.19/月 → 100GB 基本用不到 |

按现有内容量，100GB 是冗余容量；若真扩到 100GB（约 7,000 条 45s），仅存储 ¥8–12/月，¥10 必然不够。

**结论三：¥10 的可持续区间 = 播放流量 ≤40GB/月（约 2,860 次播放）+ 存储转码 ≤¥1。**

| 阈值 | 流量 | 折算成本 | 约当播放 | 动作 |
|------|------|----------|----------|------|
| 60% | 30GB | ¥6.0 | 2,140 次 | 内部告警 |
| 80% | 40GB | ¥8.0 | 2,860 次 | 告警运营，准备降级 |
| 降级线 | 45GB | ¥9.0 | 3,210 次 | 官方视频降为「首帧图 + 按需加载」 |
| 硬上限 | 50GB | ¥10.0 | 3,570 次 | 官方视频全关，仅保留图片 |

> 用户从 100 涨到 300 时流量线性到约 ¥16，**必然超 ¥10**——预算与人数线性相关，与主 PRD RK-15 同构。

### 9.4 成本护栏

| 编号 | 护栏 | 阈值 | 动作 |
|------|------|------|------|
| NFR-A21 | 官方内容月成本 | ¥10 硬上限 | 60%/80% 告警，100% 降级图片模式 |
| NFR-A22 | 官方媒体月播放流量 | ≤40GB | 超 40GB 告警，超 45GB 降级 |

## 十、复核机制（单人默认 / 双人可选）

### 10.1 两种模式

| 模式 | 适用 | 规则 |
|------|------|------|
| `single`（默认） | 只有 1 个后台账号 | 提交人自查后发布；**必须**完成 8 项清单 + 10 秒冷却 + 二次确认；内容打 `single_review=1`；自动入待抽查队列 |
| `dual` | 有第 2 个账号且具复核权限 | 提交人与复核人**必须**不同；可驳回并填原因；未复核 24h 自动失效 |

切换：配置项 `official_review_mode`，≤60 秒生效，**不改代码不发版**。第 2 个账号创建后系统提示"可切换为双人复核"。

### 10.2 单人模式 8 项发布检查清单（强制逐项勾选）

| # | 检查项 | 不通过的后果 |
|---|--------|--------------|
| 1 | 标题与正文无错别字、无占位符残留 | 官方内容出错，公信力受损 |
| 2 | 无疗效/效果承诺、无绝对化用语（最/第一/保证） | 违反广告法与平台规则 |
| 3 | 引用的训练数据为官方号自有，未使用任何用户数据 | 侵犯用户隐私 |
| 4 | 图片/视频素材来源与授权已逐项登记 | 版权风险 |
| 5 | 动作要领与常见错误已由有训练背景的人核对 | 错误指导导致受伤争议 |
| 6 | 嵌入卡片引用对象未删除、数据正确 | 卡片空占位 |
| 7 | 双端预览（Web + 小程序）均已检查 | 一端排版错乱 |
| 8 | 已确认发布时间与下线时间（公告必填） | 公告长期挂着不撤 |

> 单人模式下这 8 项是**唯一自检关口**。勾选记录随内容存档，审计可见"谁在何时确认了哪 8 项"。

### 10.3 待抽查队列

| 规则 | 要求 |
|------|------|
| 入队 | `single_review=1` 内容自动入队，保留 30 天 |
| 自检 | 发布后 **24h 内**提交人对照 8 项自查并记录结论 |
| 抽查 | 每月 **≥30%**（不足 3 条则全查）；抽查人 = 业务方或上级（只读账号即可） |
| 结论 | 通过 / 需修改（24h 内处理）/ 立即下线 |
| 升级 | 不合格率 >10% → 触发"是否补第 2 人"复盘 |

## 十三、业务流程与状态机

### 13.1 动作变更

```
新建/编辑 → 字段校验（枚举/长度/重名/别名冲突）
   ├─ 失败 → 定位字段，保留输入（出口：修正后重提）
   └─ 通过 → 是否改敏感字段？
        ├─ 否 → 预览 → 发布 → ≤60s 生效 + 版本
        └─ 是 → 影响评估（记录/用户/PR/口径）
                 ├─ 未选策略 → 发布按钮置灰
                 ├─ 不追溯 → 发布（仅新记录）
                 └─ 全量重算 → 超管审批 → 异步任务
                        ├─ 失败 → 保留进度，前台维持旧口径（出口：续跑/放弃）
                        └─ 完成 → 通知 → 生效 + 版本 + 审计
异常：无权限（按钮置灰）；草稿被他人编辑（只读可接管）；重算期间新写入按旧口径，完成后统一切换
```

### 13.2 动作合并

```
选 A + B → 校验
   ├─ B 已归档/已合并 → 阻断，提示链式重定向
   ├─ A 或 B 为自建 → 阻断
   └─ 通过 → 展示影响条数 → 二次确认（输入 B 名称）
        → A.archived=1 + redirect_to=B + 写 redirects + 审计
异常：执行中断 → 事务回滚（A 不归档）；重复合并 → 幂等返回"已合并"
出口：动作列表（A 带"已合并"标记）
```

### 13.3 官方内容发布

```
起草（官方号）→ 块 JSON 校验 → 机审（同步）
   ├─ 高危命中 → 拦截并标位置
   └─ 通过 → 素材授权校验
        ├─ 未登记 → 提交按钮禁用
        └─ 已登记 → single？勾 8 项 → 10s 冷却 → 发布
                     └ dual？提交复核 → 24h 未复核则失效
        → 立即/排期发布
             ├─ 排期时内容已下线 → 跳过并告警
             └─ 到点 → 前台 ≤1 分钟可见
已发布 → 编辑 → 回草稿重走复核（线上旧版继续可见）
已发布 → 下线 → 不可见 + 旧链接提示 + 数据保留
```

### 13.4 配置变更

```
选配置 → 改值 → 类型/范围/依赖校验
   ├─ 失败 → 指出具体项
   └─ 通过 → 风险级判断
        ├─ 低 → 原因 → 二次确认 → 即时生效
        ├─ 中 → 原因 + 影响说明 → 二次确认 → ≤60s 生效
        └─ 高 → 提交 → 双人复核（单账号期：二次确认 + 强制原因 + 进摘要）→ 生效
异常：复核人=提交人（阻断）；生效后端未确认（显示待确认并告警）
出口：配置详情（历史可见，可回滚）
```

### 13.5 状态机

**动作**：草稿 → 待发布 → 已发布 →（已归档 ⇄ 已发布）／已合并（终态）

**官方内容**：草稿 → 待复核 → 已排期 → 已发布 →（已下线 ⇄ 已发布）／已驳回 → 草稿

**配置**：当前值 → 待确认（高风险）→ 生效 →（已回滚）

**审核**：待审 → 通过 / 限流 / 下架 / 账号处置（全部留痕，下架可申诉，申诉可判误判）

## 十五、权限与安全

### 15.1 权限矩阵

| 模块 | 一期（1 账号 super_admin） | 扩人后（4 角色） |
|------|----------------------------|------------------|
| 动作库（安全字段） | 全权 | 超管/运营写，审核员只读 |
| 动作库（敏感字段/重算） | 全权（需二次确认 + 原因） | 运营写，超管审批 |
| 动作合并 | 全权（输入名称确认） | 运营提交，超管审批 |
| 官方内容 | 全权（single 下受 8 项约束） | 运营写，复核人确认（dual） |
| 审核队列 / 举报 / 申诉 | 全权 | 审核员处理，主管复核申诉 |
| 配置（低/中） | 全权 | 超管/运营 |
| 配置（高） | 全权（二次确认 + 原因 + 摘要） | 双人复核 |
| 用户处置 | 全权（永久封禁仅超管） | 超管/运营 |
| 看板（含成本） | 全权 | 审核员不可见成本 |
| 审计 | 全权 | 超管全量，其余仅本人 |
| 账号管理 | 全权 | 仅超管 |

### 15.2 安全要求

1. **鉴权双保险**：前端隐藏 + 后端逐接口校验 + 对象级校验。
2. **账号物理隔离**：`admin_accounts` 与 `users` 不同表，避免前台提权直通后台。
3. **数据最小化**：默认不展示训练明细与媒体原件；工单授权 24h 失效并留痕。
4. **审计不可篡改**：库层仅 INSERT/SELECT；应用层无删除接口；导出本身也记日志。
5. **高风险四件套**：二次确认 + 原因必填 + 复核（高风险）+ 可回滚。
6. **合规边界**：官方内容禁疗效承诺、绝对化用语、诱导分享；素材必须登记授权。
