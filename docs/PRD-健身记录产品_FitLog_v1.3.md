## 二、背景与目标

### 2.1 背景

训练者当前的工具链是割裂的：

1. **数据在工具里**：力量/有氧数据记在记录类 App（或纸笔、备忘录），能看重量和次数，但看不了"为什么练、练完什么感受"。
2. **内容在平台里**：训练复盘、动作讲解、阶段性总结写在公众号/小红书/Notion，图片视频在手机相册，与训练数据完全脱钩。
3. **打卡在第三个地方**：习惯类打卡应用只记"今天打了卡"，不认"今天到底练了什么"，容易出现空打卡、数据不可信。

结果是：**练了三年，翻不到一次完整的"那段时间我怎么练的"**——数据、影像、文字三份资产分散，无法沉淀成个人成长档案，也无法顺畅地对外表达。

同时，市面主流产品的能力边界很清晰（见 2.2）：极简记录类不做内容，内容社区类不做深度记录，跨端能力普遍偏弱（部分记录工具至今无 Web 端）。

### 2.2 市面竞品调研结论

> 调研方式：公开产品官网/官方应用商店描述/第三方横向评测文章（2025–2026）。仅借鉴通用功能模式与信息架构，不复刻任何产品的文案、视觉与专有内容。

| 产品 | 形态 | 核心能力 | 内容 / 社交 | 对我们的启示 |
|------|------|----------|-------------|--------------|
| Jefit | iOS/Android/手表/Web | 1500+ 动作库、5×5 / PPL 等计划模板、组次重量记录、容量与 1RM 曲线、肌群频率热图、身体数据 | 共享训练计划、社区 | 跨端齐全 + 动作库 + 容量/1RM 口径成熟，是"记录深度"的基准线 |
| Strong | iOS/Android/手表 | 极简快速记录（一组 3 步内完成）、休息计时、常规模板（免费限 3 个）、进阶图表 | 无社交（刻意不做） | 记录速度是留存关键；**无 Web 端是明显缺口** |

**三条共性空白（我们的机会点）**

1. **记录与内容不在一处**：强记录的工具不写文章，能写文章的平台不认训练数据。
2. **双端分工缺失**：桌面端适合写长文、看趋势；手机端适合记录、拍照、打卡。少有产品把这件事分工做清楚。
3. **打卡与训练脱钩**：多数打卡只认"打过卡"，不认"练了什么"，导致数据不可信、复盘无价值。

### 2.3 借鉴与取舍（明确不照搬的部分）

| 借鉴（通用模式） | 取舍说明 |
|------------------|----------|
| 动作库 + 组次重量 + 1RM / 容量双口径 | 采纳，作为记录核心；口径自建定义（见第三章） |
| 计划模板（如 5×5、推拉腿） | 一期只做"用户自建模板"，官方模板置 v1.2 |
| 快速记录（少点击、记住上次数据） | 采纳为一期硬指标：记一组 ≤3 次点击 |
| 打卡成就与连续天数 | 采纳，但**打卡必须绑定真实训练记录**（差异化） |
| 数据动态 feed / 关注 | **一期不做**，仅做结构与 UI 预留（见 7.9） |
| 课程体系 / AI 动作纠错 / AI 训练编排 / 电商 / 硬件 | 一期不做，不进本期范围 |
| 竞品视觉风格、文案、图标 | 不参照、不复刻，独立设计 |

### 2.4 产品定位

> **一句话**：一个以「训练记录」为地基、以「图文视频内容」为表达方式的个人健身成长档案；手机端负责记录与打卡，桌面端负责沉淀与复盘；社区留位，先长出内容。

三层价值递进：

| 层 | 用户得到的 | 产品形态 |
|----|-----------|----------|
| 地基 | 每次训练都有据可查（重量、次数、组数、时长、体感、影像） | 训练记录 + 媒体上传 |
| 表达 | 训练可以写成文章：数据卡片直接嵌进长文，图文视频一体 | 块编辑器 + 文章发布 |
| 坚持 | 有记录才算打卡，连续天数与月历可视化 | 打卡体系 |
| （预留）连接 | 内容可被看见、被讨论 | 公开页 → 社区（v1.2 起） |

### 2.5 目标用户

| 角色 | 特征 | 核心诉求 | 优先级 |
|------|------|----------|--------|
| 记录型训练者 | 有固定训练计划，健身房/居家，每周 2–5 练 | 快速记录、看到进步、翻得到历史 | P0（核心） |
| 内容型训练者 | 有表达欲，会写训练复盘/动作讲解 | 数据与图文视频在同一处成文，一键发布 | P0 |
| 习惯建立者 | 新手或回炉，目标是"先坚持下来" | 轻量打卡、连续天数、轻量提醒 | P1 |
| 私教/教练 | 需要给学员留训练说明 | 内容可分享（暂以公开页承载） | P2（v1.2 评估） |
| 平台运营/审核 | 内部角色 | 内容审核、举报处理、数据看板 | P1（内部后台） |

### 2.6 成功指标与口径

**北极星指标**：**周有效记录用户数（WAR）**

- 口径：自然周（周一 00:00 至周日 23:59，按用户注册时区）内，**≥2 个不同日期存在至少 1 条训练记录**的去重用户数。
- 排除：仅浏览、仅打卡无记录、仅上传媒体未生成记录的用户。

| 指标 | 口径 | 目标（估算，需上线后校准） |
|------|------|--------------------------|
| 激活率 | 注册后 24h 内完成 ≥1 条训练记录 且 ≥1 次打卡的用户 ÷ 当日注册用户 | ≥40% |
| 记录频次 | 周人均训练记录条数 | ≥2.5 |
| 次周留存 | 首周有记录的用户，第 2 周仍产生记录的比例 | ≥35% |
| D30 留存 | 注册后第 30 天仍活跃 | ≥15% |
| 图文发布率 | 周内有 ≥1 篇发布文章的用户 ÷ 周活跃用户 | ≥8% |
| 打卡连续度 | 连续打卡 ≥7 天的用户占比 | ≥20% |
| 上传成功率 | 媒体上传成功数 ÷ 发起数（按网络类型分组） | Wi-Fi ≥98%，4G ≥95% |
| 记录效率 | 追加一组的端到端点击数（含输入） | ≤3 次点击 |
| 人均存储用量 | 计费用量（转码产物 + 封面，不含原件）÷ 有媒体上传的用户数 | **目标 ≤1.5GB**（配置 B，v1.2 由 6GB 下调） |
| 月度外部成本 | 存储 + 流量 + 转码合计 | **≤¥20 / 月**（硬上限，NFR-23a） |
| 预算闸门触发 | 当月是否触发 FR-91 | ≤1 次 / 月 |
| 社区占位点击率 | 点击「敬请期待」入口的用户 ÷ 周活用户 | 观察值，≥8% 视为社区需求信号成立（D-08 触发条件） |
| 水印使用率 | 勾选加水印的视频数 ÷ 视频发布数 | 观察值，用于判断品牌水印是否需要改默认 |

> 注（v1.2）：上述目标值按公测规模测算。**当前内测 ≤100 人时样本过小，指标只作方向参考、不作考核**；内测期只盯两项硬指标——记录链路成功率（session_saved ÷ session_start ≥92%）与月度成本不超支（≤¥20）。

## 三、名词与术语定义

| 术语 | 定义 |
|------|------|
| 训练记录（Session） | 一次训练活动，包含日期、开始/结束时间、动作条目、备注、媒体、体感评分 |
| 动作条目（Exercise Item） | 训练记录中的一个动作，含动作库引用与若干组 |
| 组（Set） | 一次连续完成的重复动作，记录重量、次数、RPE 或时长/距离 |
| 容量（Volume） | 力量：Σ(重量 × 次数)，单位 kg；有氧：时长或距离，不进容量口径 |
| 估算 1RM | 由已记录组次推算的单次最大重量，采用 Epley 公式：`1RM = w × (1 + reps ÷ 30)`；仅对 reps ≤12 的组计算，页面标注"估算值" |
| 个人纪录（PR） | 某动作在指定口径（估算 1RM / 单组最大重量 / 单组最大次数）上的历史最优 |
| 块（Block） | 编辑器的最小内容单元（段落、标题、图片、视频、引用、列表、分割线、嵌入卡片） |
| 嵌入卡片（Embed） | 可在文章中引用的结构化卡片：训练记录卡、打卡卡、动作卡 |
| 打卡（Check-in） | 以自然日为单位的完成标记，来源为"自动（当日有训练记录）"或"手动补记" |
| 连续天数（Streak） | 从最近一次打卡日向前，连续未中断的打卡天数 |
| 媒体资产（Media） | 用户上传的图片或视频，含原件、转码产物、封面、审核状态 |
| 公开页 | 用户主动发布的文章或训练记录的只读页面，可被未登录用户访问（受审核与隐私开关约束） |
| 社区位 | 预留给 feed / 关注 / 评论的产品入口与数据结构，一期**只显示「敬请期待」占位、不开放功能**（D-08） |

## 五、方案对比与选型说明

### 5.1 候选方案

| 方案 | 思路 | 一期重点 |
|------|------|----------|
| A：记录优先，内容跟进 | 先把"记录 + 上传 + 打卡"做到极快极稳，再长出内容能力 | 记录闭环、媒体链路、打卡 |
| B：内容优先，社区驱动 | 先做块编辑器与公开内容，用内容吸引人，再补记录 | 编辑器、公开页、分享 |
| C：单端先行（先 Web 或先小程序），另一端后续补 | 降低一期复杂度 | 单端完整闭环 |

### 5.2 对比

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 实现成本 | 中 | 中高 | 低 |
| 开发复杂度 | 中（媒体链路是主难点） | 高（编辑器 + 审核 + 两端渲染一致） | 低 |
| 用户体验 | 记录快、地基稳；内容能力后到 | 表达强，但缺数据的文章说服力弱 | 单端可用，跨端断裂体验差 |
| 风险 | 内容增长慢 | 冷启动难（无记录数据支撑内容）、审核风险前置 | 与"双端"诉求冲突 |
| 上线速度 | 快 | 慢 | 最快 |
| 综合评价 | **推荐主线** | 作为 A 的后续阶段 | 不采用（与需求冲突） |

### 5.3 推荐与理由

**推荐方案 A，并采用"双端分工、分期交付"的演进路径。**

理由：

1. 记录是本产品的**不可替代地基**——没有真实训练数据，嵌入卡片、成长曲线、可信打卡全部落空，内容也就退化为普通图文工具。
2. 竞品已验证：记录速度与稳定性直接决定留存（记录类工具的差异化就在"快"）。内容能力可以做晚，记录不能做差。
3. 社区待定，一期用"公开页 + 审核链路"低成本试水，既验证内容供给意愿，又不承担社区运营成本。

**演进路径（本期 → 后续 + 触发条件）**

> v1.2 补充：以下阶段是**能力演进**，不等于**规模演进**。规模扩张以预算增长为前提（¥20 → N 倍），否则会先后撞上预算闸门（FR-91）与容量瓶颈。

| 阶段 | 内容 | 进入下一阶段的条件 |
|------|------|--------------------|
| V1.0（Web 主线） | 记录 + 媒体上传 + 块编辑器（Web 完整版）+ 打卡 + 公开页 | 激活率 ≥35% 且 上传成功率达标 |
| V1.1（小程序补齐） | 小程序记录（轻量）+ 拍照/视频上传 + 打卡 + 轻量编辑 + 分享 | 双端周活比例稳定，小程序次周留存 ≥30% |
| V1.2（内容增强） | 官方模板、文章模板化、内嵌数据看板、内容推荐位（编辑精选） | 图文发布率 ≥8% |
| V1.3（社区评估） | feed / 关注 / 评论 / 举报（需完成审核与运营人力评估） | **占位点击率 ≥8%、说明页停留 ≥15s**（D-08），且公开页 UV 与内容供给达阈值、审核人力就位 |
| V1.4（智能与生态） | 训练建议、穿戴数据接入、教练协作 | 数据量与留存支撑 |

## 六、用户角色与使用场景

### 6.1 用户画像（基于需求描述构建，标注为待验证假设）

**画像 A：李衡，29 岁，健身房训练 2 年**

- 目标：深蹲/卧推/硬拉稳定进步，看清 8 周训练周期效果
- 现状：用手机备忘录记重量，练完拍几张照片发朋友圈，月底想复盘发现什么都没有
- 痛点：记录要点击太多次；练完想写点感受没地方写；三个月前的数据翻不到
- 能力水平：熟练（会用模板、懂 RPE）

**画像 B：周颖，25 岁，居家跟练 + 瑜伽，训练 8 个月**

- 目标：坚持下来，体重和围度有变化
- 现状：在小红书发打卡图，用另一款 App 记体重
- 痛点：打卡和真实训练脱钩，"今天到底练没练"说不清；图太多找不到
- 能力水平：新手偏熟练

**画像 C：陈默，33 岁，健身内容作者**

- 目标：把训练方法写成系统长文，带自己的训练数据做例证
- 现状：Notion 写稿 → 截图数据 → 排版 → 发公众号
- 痛点：截图数据易过期、视频要另外传、排版来回折腾
- 能力水平：熟练

## 七、功能需求

> 状态词约定：**必须（shall）** / **应该（should）** / **可以（may）** / **禁止（must not）**。验收标准用 Given / When / Then。

### 7.1 账号与身份（M1）

| 编号 | 需求 | 规则 | 验收标准 |
|------|------|------|----------|
| FR-01 | 小程序登录 | 必须支持微信一键登录（静默取 openid，首次需授权头像昵称，可跳过） | Given 新用户首次打开小程序，When 点击"微信登录"，Then 3 秒内进入记录页，昵称可后补 |
| FR-02 | Web 登录 | 必须支持手机号 + 短信验证码；应该支持小程序扫码登录 | Given 用户已在小程序登录，When 在 Web 扫码确认，Then 双端进入同一账号，数据一致 |
| FR-03 | 双端同账号绑定 | 同一手机号绑定后，小程序与 Web 必须指向同一 user_id；禁止生成两个账号 | Given 手机号已绑定微信，When 用该手机号在 Web 登录，Then 看到与小程序完全相同的记录列表 |
| FR-04 | 游客体验 | 可以允许未登录浏览公开页；禁止未登录写入任何数据 | Given 未登录用户，When 尝试点击"开始训练"，Then 弹出登录引导，返回后继续原操作 |
| FR-05 | 账号注销 | 必须提供注销入口；注销后 30 天内可撤销，超期彻底删除（含媒体原件与转码产物） | Given 用户申请注销，When 满 30 天且未撤销，Then 账号与全部媒体不可恢复，且返回删除完成通知 |

### 7.2 训练记录（M2）

**记录类型**：力量训练、有氧训练、自重/拉伸、其他（自定义）。

| 编号 | 需求 | 规则 | 验收标准 |
|------|------|------|----------|
| FR-06 | 开始/结束训练 | 必须支持"开始训练"计时与"补记"（手动选日期时间） | Given 用户点击开始训练，When 结束训练，Then 生成一条 Session，含开始/结束时间与总时长 |
| FR-07 | 添加动作 | 必须支持搜索动作库、最近使用、收藏；应该支持自定义动作 | Given 用户在记录页搜索"卧推"，When 选择结果，Then 该动作加入本次训练并自动带出上次同动作数据 |
| FR-08 | 记录一组 | 必须记录重量、次数；RPE 可选；重量支持 kg/lb 切换（仅展示换算，存储统一 kg、精度 0.5） | Given 已有动作条目，When 输入 60 / 8 并确认，Then 组记录生成，且仅需 3 次点击（含确认） |
| FR-09 | 记住上次 | 必须在同动作新增组时预填上一次同动作的重量与次数 | Given 上次卧推 60kg×8，When 今天新增卧推组，Then 预填 60 / 8，用户可直接确认 |
| FR-10 | 组类型 | 必须支持普通组、热身组（不计入容量）、递减组、超级组（两个动作关联） | Given 一组标记为热身组，When 计算当日容量，Then 该组不计入 |
| FR-11 | 有氧记录 | 必须记录时长；应该记录距离、平均心率（手动）；必须记录类型（跑步/骑行/椭圆/跳绳/其他） | Given 记录 30 分钟跑步 5km，When 保存，Then 概览显示时长与距离，容量口径为空 |
| FR-12 | 体感与备注 | 应该支持组备注（如"右肩紧"）与整场备注；可以支持 1–5 星体感评分 | Given 用户填写备注，When 下次查看该动作历史，Then 备注可见 |
| FR-13 | 训练模板 | 必须支持把一次训练保存为模板并从模板开练（动作与组数预设、重量留空） | Given 用户保存"推日"模板，When 下次从模板开始，Then 动作与组数自动填充 |
| FR-14 | 休息计时 | 应该提供组间休息计时（默认 90s，可按动作记忆） | Given 完成一组，When 计时开始，Then 到点提醒（小程序震动/提示音，Web 页面提示） |
| FR-15 | 离线记录 | 必须支持断网下继续记录，恢复网络后自动同步；冲突以"服务端最后写入为准 + 本地保留待同步副本" | Given 飞行模式下记录 3 组，When 恢复网络，Then 3 组在 10 秒内同步成功且无重复 |
| FR-16 | 编辑与删除 | 必须支持修改/删除已保存的组与整场训练；删除训练须二次确认，并联动重算当日打卡与 PR | Given 删除当日唯一训练，When 确认删除，Then 当日打卡自动回退为未打卡，PR 重新计算 |
| FR-17 | 记录列表 | 必须按时间倒序分页（每页 20 条）；必须支持按类型/月份筛选 | Given 用户有 200 条记录，When 滚动到底，Then 加载下一页且不重复 |
| FR-18 | 快速补记 | 应该支持"30 秒补记"：只填类型 + 时长 + 一句备注即可完成，便于漏记补救 | Given 用户点"快速补记"，When 只填 3 项提交，Then 生成 Session 并计入打卡 |
| FR-19 | 单位与格式 | 必须支持 kg/lb、km/mile 展示切换；数值输入禁止科学计数法与负数 | Given 用户切换到 lb，When 查看历史，Then 全部数值按换算展示，存储值不变 |
| FR-20 | 数据校验 | 重量 0–1000kg、次数 0–1000、时长 0–24h；超限必须拦截并提示 | Given 输入重量 2000，When 提交，Then 提示"请输入 0–1000 之间的重量"，不保存 |

### 7.4 媒体上传（M4）

> **技术约束（重要，直接影响交互设计）**
> - 小程序云开发 `wx.cloud.uploadFile` 单文件约 5MB 上限（来源：微信云开发实践文档），**视频不可走此通道**，必须使用对象存储（COS/OSS）分片直传 + 服务端签名。
> - 微信云存储单文件通常 50MB 上限（部分资料称企业版更高），自建对象存储更灵活，故一期采用自建 COS + CDN。
> - 以上限制以微信官方文档当前版本为准，研发需在方案评审时复核。
> - **配额口径（v1.2 更新，必须与前端文案一致）**：50GB = 账号下所有媒体的**计费用量**，即「720p 转码产物 + 封面帧 + 30 天内暂存的原件」之和，按资产去重（同一资产被多篇文章引用只计 1 份）。v1.2 起不再保留 480p 档与长期原件（FR-29），计费条目相应减少。**但配额只是上限，实际约束是全局预算闸门（FR-91）**——界面上必须同时表达这两件事，否则用户会认为"明明还有空间却传不上去"是 Bug。

| 编号 | 需求 | 规则 | 验收标准 |
|------|------|------|----------|
| FR-25 | 图片上传 | 必须支持拍照/相册多选（单次 ≤9 张）；客户端压缩至长边 ≤1920px、≤500KB（质量自适应，禁止低于 0.6 质量） | Given 选择 9 张 5MB 照片，When 上传，Then 全部在 30 秒内（Wi-Fi）完成且可预览 |
| FR-26 | 视频上传 | 必须支持相册选择与拍摄；产品限制：单个 ≤200MB、≤3 分钟、≤1080p；超限必须提示并引导改用 Web 端上传 | Given 选择 5 分钟视频，When 上传，Then 拦截并提示"视频请在 3 分钟内，或到电脑端上传"，不发起上传 |
| FR-27 | 分片直传 | 必须走"申请凭证 → 分片直传对象存储 → 完成回调"链路；必须携带上传会话 ID 以支持断点续传 | Given 上传中断（切后台/断网），When 重新进入，Then 从已传分片续传，不从头重传 |
| FR-28 | 上传进度与取消 | 必须显示单文件进度与整体进度；必须可取消，取消后清理已传分片 | Given 上传中点击取消，When 确认，Then 停止上传并在 1 分钟内清理服务端分片 |
| FR-29 | 转码与封面（v1.2 调整） | 必须转码出 **720p 单档**（取消 480p 双档，节省约 30% 存储，见 D-11）+ 自动抽帧封面；**视频原件不入库长期保存**（30 天后清理，见 FR-91）；转码完成前展示处理中状态 | Given 视频上传完成，When 60 秒素材，Then P95 在 3 分钟内产出可播放地址（720p） |
| FR-30 | 压缩与格式 | 必须兼容 HEIC/HEVC（服务端转 JPEG/H.264）；单文件格式不支持时提示具体格式 | Given 上传 iPhone HEIC 照片，When 完成，Then 其余端可正常显示 |
| FR-31 | 隐私与位置 | 必须默认剥离 EXIF 地理位置；必须提供"模糊/移除位置"开关且默认开启 | Given 上传带 GPS 的照片，When 下载原图，Then 不含 GPS 信息 |
| FR-32 | 存储配额（v1.2 调整） | 账号配额为 **50GB（计费用量口径，见本节技术约束）**，但**必须叠加全局预算闸门（FR-91），配额是上限、预算才是实际约束**；必须展示"已用 / 50GB"与分类型占用；达到 80% 提示，100% 禁止上传。**护栏**：① 单用户日上传 ≤500MB（NFR-22）；② 单文件受 FR-26 的 200MB / 3 分钟限制；③ 30 天未访问的转码产物转低频；④ 不保留视频原件（FR-29）；⑤ 删除后 24h 内释放计费用量；⑥ 用量明细可查。**文案禁止**：不得出现"50GB 随便传""无限空间"等表述，必须同时说明"当前为小范围内测，存储按预算限量" | Given 已用 49.8GB，When 再传视频，Then 拦截并提示剩余空间、占用明细与清理建议；Given 全局预算已达上限，When 任何用户发起视频上传，Then 按 FR-91 降级为"仅图片"，并说明原因 |

| FR-83 | 品牌水印（v1.3 定版：中文文字标「练迹」） | **可选、非强制、默认关闭**；仅对视频生效，图片不加。位置固定**左上角**：距左 4%、距上 4%。**字号按文字高度定义**（不按宽度百分比，中文 2 字按宽度算会偏小且不稳定）：文字高度 = **视频高度的 4.5%**（1080p ≈ 48px，720p ≈ 32px），宽度自适应，2 字约占画面宽 9%，下限 24px、上限 64px。**内容为「练迹」**（中文标，上线前需完成商标检索；英文 FitLog 仅用于界面，不用于水印）。**不透明度 90%**，白色 #FFFFFF + 1px 深色描边 `rgba(0,0,0,0.35)`——**用描边解决深浅背景可读性，不需要深色背景反转素材**。禁止用户自定义上传水印。竖屏视频必须避让顶部安全区（下移至状态栏下方 ≥24px 或按机型安全区），禁止被刘海/状态栏/系统控件遮挡 | Given 勾选水印并上传 1080p 竖屏视频，When 转码完成，Then 「练迹」二字位于左上角、完整可见、在纯白与纯黑背景上均可辨认，且未被顶部控件遮挡 |

| FR-82 | 未成年人保护 | 必须不设诱导性付费与打榜；涉及未成年用户时按平台要求提供监护相关能力（如青少年模式提示）；不得展示减肥/增肌效果承诺 | Given 内容含"保证减肥效果"表述，When 审核，Then 判定不通过并提示修改 |

### 7.11 内容审核体系（v1.1 新增 · 自建）

> **口径澄清（重要）**：业务方决策为"审核自建"。自建指**自建审核团队 + 自建审核后台与流程**；机器审核仍必须接入第三方内容安全能力，因为发布动作是实时的，纯人工无法在发布前完成拦截。若"自建"的意图是连机审也自研，需单独立项评估（周期与成本远高于前者），本期按"机审外采 + 人审自建"执行。

**三层链路**

```
用户发布 → ① 机审（同步，文本+图片+视频帧/音轨） → 命中高危：直接拦截
                                              → 命中疑似 / 抽中：转 ② 人审
                                              → 未命中：先限制可见范围发布（仅自己），人审通过后转公开
② 人审（自建后台队列） → 通过 / 限流 / 下架 → 留痕
③ 举报（用户入口） → 工单 → 复核 → 结论 + 申诉
```

| 编号 | 需求 | 规则 | 验收标准 |
|------|------|------|----------|
| FR-85 | 审核前置 | 公开内容**必须**在通过机审后才允许出现在任何列表/公开页；未完成人审的内容默认仅自己可见，禁止"先公开后审核" | Given 一篇内容机审通过但人审未完成，When 他人访问链接，Then 提示内容暂不可见 |
| FR-86 | 自建审核后台 | 必须提供队列（按风险分优先级）、内容预览（含视频逐帧/抽帧）、判定（通过/限流/下架/账号处置）、原因选择、备注、留痕（操作人+时间+原因）、误判复核 | Given 审核员判定下架，When 作者查看，Then 看到下架原因与申诉入口，后台可追溯到该操作 |
| FR-87 | 审核 SLA | 必须按下表执行，超时内容自动维持不可见状态（宁可不上线，不放过） | Given 一条内容进入人审队列 24h 未处理，When 用户查看，Then 仍为仅自己可见，并提示"审核中" |
| FR-88 | 申诉 | 必须提供申诉入口；作者可提交一次申诉，审核主管复核，48h 内答复；申诉成功恢复内容且不计入违规次数 | Given 作者申诉成功，When 内容恢复，Then 原下架记录标记"误判"，不计入账号违规 |
| FR-89 | 审核规则库 | 必须把判定标准文档化并版本化（规则编号、判定示例、处置档位），新增规则需评审；规则变更后对历史内容不做追溯（除非高危） | Given 规则库 v2 新增一条标准，When 审核员查看待审内容，Then 界面显示适用规则编号 |
| FR-90 | 审核数据看板 | 必须展示：日审核量、机审命中率、人审通过率、平均处理时长、申诉率、误判率；异常（如命中率突增）必须告警 | Given 某日机审拦截率突增至 30%，When 触发告警，Then 运营 2h 内介入排查 |
| FR-92 | 公开内容每日名额（v1.2 新增 · 审核人力后置的兜底） | 审核人力负责人未定（D-12），故公开内容必须**走"名额制"而非无限开放**：① 初期全站公开名额 **20 条/日**（全局，非每用户）；② 超出名额的发布请求自动降为"仅自己可见"并进入次日队列，用户可编辑后重提，**内容不得丢失**；③ 名额值为运营旋钮，人力未到位不得上调；④ 必须指定至少 1 名当值审核人（可兼任），空缺时全部公开内容停在"仅自己可见"；⑤ 公开列表（feed）一律不开放，仅保留单篇链接访问 | Given 今日第 21 篇提交发布，When 用户点发布，Then 提示"今日公开名额已用完，已保存为仅自己可见，明日优先处理"，草稿与内容完整保留 |

> **"先做产品"的可行解法（v1.2 说明）**：业务方要求审核人力后置（D-12），这不阻塞开发——把公开能力做成"名额 + 开关"，产品功能全部做完，开放度由旋钮控制；人力到位后调大名额即可，不需改代码。代价是早期公开内容量很小、增长慢，需接受。

**审核 SLA（v1.1 定版）**

| 环节 | 时限 | 说明 |
|------|------|------|
| 机审返回 | 发布请求内同步完成，P95 ≤3s | 超时则降级为"仅自己可见" |
| 高危命中人审 | 15 分钟内响应 | 未响应期间内容不对外可见 |
| 常规人审（抽检 / 新用户首 3 篇 100%） | T+24h | 抽检率 ≥20% |
| 举报首次响应 | 24h 内 | 涉及人身安全、未成年、诈骗类 2h 内 |
| 举报结论 | 48h 内 | 与 v1.0 一致，超时须向举报人反馈进展 |
| 申诉答复 | 48h 内 | 由审核主管处理 |
| 覆盖时段 | 7×12（09:00–21:00） | **夜间仅机审 + T+1 复核，属已知风险，已在 RK-13 记录** |

**判定档位（必须留痕）**

| 档位 | 适用 | 用户可见后果 |
|------|------|--------------|
| 通过 | 无风险 | 正常发布 |
| 限流 | 轻度擦边、疑似导流 | 仅自己可见，不进入任何列表，通知作者 |
| 下架 | 明确违规 | 立即不可见，通知原因，允许 1 次申诉 |
| 账号处置 | 重复违规（7 日内 ≥3 次下架） | 禁发 7 天 / 30 天；必须人工复核后执行 |

**人力量级（估算，需运营确认）**

| 阶段 | 日发布量（估算） | 需人审量 | 人力 |
|------|------------------|----------|------|
| M2 内测（50 人） | <20 篇 | 全审 20 | 0.2 人（产品/运营兼任） |
| M3 Web 公测 | 100–300 篇 | 40–100 | 0.5–0.8 人 |
| M4 双端放量 | 300–800 篇 | 100–250 | 2 人轮班（7×12）+ 0.5 主管 |

> 结论：内测期 1 人可启动；**双端放量前必须补到 2 人轮班，否则 SLA 无法兑现**。人力未到位前，公开内容的开放比例应通过配额控制（每日公开名额）。

### 8.5 成本护栏与预算闸门（v1.2 定版 · 由 50GB 配额 + ¥20 预算派生）

**单用户成本拆解（配置 B 典型用户，单价为行业量级估算，最终以供应商报价为准）**

| 成本项 | 假设 | 量级单价 | 单用户月成本 | 占比 |
|--------|------|----------|--------------|------|
| 标准存储 | 存量约 1GB/人 | ¥0.12/GB/月 | ≈¥0.12 | 20% |
| 低频存储 | 60% 内容 30 天后转低频 | ¥0.08/GB/月 | ≈¥0.05 | 8% |
| CDN 流量 | 月观看约 0.3GB | ¥0.20/GB | ≈¥0.06 | 10% |
| **视频转码** | 月 3 条 × 3 分钟 = 9 分钟（720p 单档） | ¥0.04/分钟 | **≈¥0.36** | **61%** |
| **合计** | — | — | **≈¥0.59 / 用户 / 月** | 100% |
| 参照：纯图片用户（无视频） | 存量 1GB | — | ≈¥0.19 | — |
| 参照：视频重度（10 条/月） | 30 分钟转码 | — | ≈¥1.40 | — |

> **关键发现（v1.2，这条比配额数字更重要）**：在 ¥20 预算下，**瓶颈是转码，不是存储**——转码约占单用户成本 61%，存储只占 20–28%。
> 这意味着：把配额从 50GB 压到 5GB 几乎省不下钱；真正有效的杠杆是**减少转码次数**（单档、限时长、按需转码、提高客户端压缩率）。因此 FR-91 的降级阶梯设计为"先限视频、后限图片"。

**结论：¥20/月 硬上限下的可承载量（v1.2 定版，替代 v1.1 的"待财务确认"）**

必须先摆平一个事实：**¥20/月 与 v1.1 的"1 万 DAU × 人均 6GB"差约三个数量级**。这两个数不能同时成立，v1.2 按"真实预算"重算。

¥20/月 能买到的量（按上面的单价折算）：

| 口径 | 折算结果 |
|------|----------|
| 全部用于存储 | 约 160GB（纯图片存量，约 500 人份） |
| 全部用于转码 | 约 500 分钟/月（≈ 55 条 3 分钟视频） |
| 折算成压缩图片 | 约 23 万张 |
| **按配置 B 混合使用** | **约 30–35 个"每月传 3 条视频"的用户**，或 **约 80–100 个纯图片用户** |

**同一 ¥20 预算下的三档配置**

| 配置 | 典型用量 | 可支撑用户 | 体验取舍 |
|------|----------|------------|----------|
| A 极简 | 存量 ≈0.5GB；视频 ≤1 条/月（60s / 480p） | ≈85 人 | 图片压至 1280px/300KB；几乎无视频 |
| **B 精简（v1.2 采用）** | 存量 ≈1GB；视频 ≤3 条/月（3 分钟 / 720p 单档） | **≈30–35 人（含视频）** / 80–100 人（纯图片） | 图片 1920px/500KB；原件 30 天后清理 |
| C 目标体验 | 存量 ≈6GB；双档 + 原件 90 天 | ≈17 人 | 即 v1.1 的成本假设 |
| （参照）v1.1 容量规划 | 6GB × 1 万人 | 1 万人 | 月成本 ¥2.5–3.5 万，约为 ¥20 的 1000 倍 |

**三条结论（必须一起读）**

1. **¥20/月 对应的是"几十人"的内测规模**：含视频约 **30–35 人**，纯图片约 **80–100 人**。因此 NFR-06 容量目标下调为"内测 ≤100 注册 / ≤40 活跃"，公测以预算增长为前提，否则容量规划与预算自相矛盾（RK-15）。
2. **50GB 配额在 ¥20 预算下不可能人均兑现**——2–3 个视频重度用户就能花光整月预算。50GB 只能作为"账号上限"存在，实际先触发的是**全局预算闸门**（FR-91）。必须如实告知用户，不能假装 50GB 可用（文案见 FR-91，D-11）。
3. 采用配置 B 后，人均约 ¥0.59/月（含视频）、¥0.19/月（纯图片）；**能覆盖多少人，取决于视频比例而不是注册人数**——这也是内测期必须盯"视频上传率"的原因。

**由此带来的产品取舍（v1.2 已落到功能需求）**

| 取舍 | 落点 |
|------|------|
| 视频只保留 720p 单档（去掉 480p：省一次转码 + 约 30% 存储） | FR-29 调整、FR-91 |
| 视频原件 30 天后清理，只留成片 | FR-91 |
| 达到预算时降级为"仅图片上传"而不是全站停服 | FR-91 降级阶梯 |
| 配额文案不得宣传"50GB 随便传" | FR-32 + FR-91 文案规则 |

| 编号 | 护栏指标 | 阈值 | 触发动作 |
|------|----------|------|----------|
| NFR-20 | 人均计费用量 | ≤1.5GB（配置 B） | >2.5GB 时：收紧**新用户**配额（老用户不追溯），并复盘上传引导 |
| NFR-21 | 预算闸门触发次数 | ≤1 次/月 | 连续 2 个月触发 → 配置由 B 降至 A，或追加预算 |
| NFR-22 | 日上传量 | ≤500MB / 用户 / 日 | 超限拦截，提示次日再传 |
| **NFR-23a** | **产品月度总成本硬上限** | **¥20 / 月**（业务方定，D-11） | 达 80%（¥16）告警；达 100% 触发 FR-91 预算闸门 |
| NFR-23b | 单用户月度成本 | ≤¥0.30 | 超标者列入观察名单，复查其用量结构 |
| NFR-24 | 冷数据占比 | 30 天未访问 ≥50% 转低频 | 低于 30% 时检查存储生命周期任务是否失效 |
| NFR-25 | 删除释放时效 | 删除后 24h 内释放计费用量 | 超时排查对象存储生命周期配置 |
| NFR-26 | 成本明细透明 | 每日产出"存储 / 流量 / 转码"三项明细 | 无明细视为不具备运营条件 |

> **计量口径（v1.3 已确认）**：¥20 = **整个产品每月的外部成本总额**（业务方确认，D-15）。因此"只够 30–35 个含视频用户"是确定结论，不是保守假设。若后续要把规模做到百人以上，必须先加预算——预算与人数是线性关系，没有技术手段可以绕开（限码率只能把系数压小，压不到 0）。

## 九、业务流程与状态流转

### 9.1 核心流程：一次完整训练

```
打开小程序 → 开始训练（计时）
  → 添加动作（搜索/最近/收藏）→ 记录组（预填上次数据）→ 组间休息计时
  → 可选：拍照/录视频（直传，后台进行）
  → 结束训练 → 填写备注与体感 → 保存
      → 服务端：写 Session → 计算容量/PR → 触发自动打卡 → 更新 streak → 生成周报增量
  → 可选：在 Web 打开该记录 → 插入文章 → 发布（审核）→ 生成公开页与分享卡
```

### 9.2 训练记录状态机

| 状态 | 触发事件 | 允许操作 | 迁移目标 |
|------|----------|----------|----------|
| 草稿（本地） | 开始训练 | 编辑、删除、同步 | 已保存 / 已废弃 |
| 已保存 | 保存成功 | 编辑、删除、插入文章、分享 | 已编辑 / 已删除 |
| 已编辑 | 修改保存 | 再次编辑 | 已保存 |
| 已删除 | 用户确认删除 | 7 天内可恢复 | 已保存 / 永久删除 |

规则：删除必须软删除 7 天；恢复入口在"最近删除"；永久删除需二次确认。

### 9.3 媒体资产状态机

| 状态 | 说明 | 迁移 |
|------|------|------|
| 上传中 | 分片传输 | → 已上传 / 已取消 / 上传失败 |
| 已上传 | 对象存储已有原件 | → 转码中 |
| 转码中 | 生成 720p/480p/封面 | → 待审核 / 转码失败 |
| 待审核 | 机审进行中 | → 可用 / 已拒绝 |
| 可用 | 可正常展示 | → 已删除 |
| 已拒绝 | 命中违规 | 保留 30 天申诉期后清理 |
| 转码失败 | 3 次重试后仍失败 | → 重试 / 删除 |

### 9.4 内容（文章）状态机

| 状态 | 触发 | 允许操作 | 迁移 |
|------|------|----------|------|
| 草稿 | 新建/自动保存 | 编辑、删除 | 待审核 |
| 待审核 | 点发布且机审命中需人审 | 编辑（撤回审核） | 已发布 / 已驳回 |
| 已发布 | 审核通过 | 编辑（重新进入审核）、下线、删除 | 已下线 / 待审核 |
| 已驳回 | 审核不通过 | 编辑后重提 | 待审核 |
| 已下线 | 作者下线或举报下架 | 编辑后重提 | 待审核 |

规则：已发布内容编辑后必须重新走审核；下架必须给出原因（作者可见，含申诉入口）。

### 9.5 打卡状态

| 状态 | 触发 | 说明 |
|------|------|------|
| 未打卡 | 当日无记录且未手动打卡 | 月历灰点 |
| 已打卡（自动） | 当日有训练记录 | 不可手动删除，随记录联动 |

| 已撤销 | 用户撤销或记录被删 | 回到未打卡，streak 重算 |

### 11.2 安全要求

1. **越权防护**：所有按 ID 的读写必须做 owner 校验，不能只依赖前端隐藏。
2. **媒体私有化**：对象存储禁止公有读；签名 URL 有效期 2h；Referer 白名单。
3. **内容安全**：文本机审（发布前）+ 图片/视频机审（转码后）+ 人审抽检；命中即拦截或转人审。
4. **审计留痕**：审核操作、下架、恢复、用户注销、数据导出必须记录操作人、时间、原因。
5. **最小采集**：不采集身份证、精确位置、通讯录；手机号仅用于登录与必要通知。
6. **数据留存**：训练与内容数据随账号存续；删除后 30 天彻底清理；被拒媒体 30 天清理。

**13.2.2 部署环境现状核查（2026-10-18，只读探测，未做任何变更）**

业务方提供的服务器为 `101.43.91.192`。实际探测结果：

| 检查项 | 现状 | 判定 |
|--------|------|------|
| 主机在线 | 80 端口 92ms 内响应 | 在线 |
| 80 端口 | 返回 **307 重定向**，页面内容为 **Next.js 应用**，且当前渲染为错误页（`__next_error__`） | 机器上**已有其他应用在跑**，且处于异常状态；新项目不能直接占用 80 端口 |
| 443 端口 | **连接超时（6s 无响应），未开放** | **小程序硬阻塞**：微信要求 HTTPS 且 TLS ≥1.2 |
| 域名 | 未提供（仅有 IP） | **硬阻塞**：小程序服务器域名必须是**已备案域名**，不支持 IP、不支持带端口 |
| SSL 证书 | 未部署 | 需部署受信任 CA 证书（自签证书不被接受） |
| ICP 备案 | 未启动 | 7–20 工作日，**备案期间网站不能对外正常提供服务** |

**结论（需要如实告知）**：这台机器目前**只能用于开发期的 IP 直连调试，不能直接承载小程序线上流量**。有服务器不等于能上小程序——缺的是"域名 + 备案 + 证书"这三件套，而其中备案是唯一无法靠技术绕过的环节。

**关于 80 端口已有应用的两条建议**

1. 若那个 Next.js 应用还要保留：新项目用 **Docker 或独立端口（如 8080/3001）**，由 Nginx 按域名做虚拟主机分流，**不要覆盖 80 端口的现有服务**。
2. 若它已废弃：先确认无数据依赖再清理，清理前做快照（避免误删造成不可恢复的损失）。

**13.2.3 上线准入链路（必须按序，缺一不可）**

```
① 域名注册（10 分钟）
   ↓
② 域名实名认证（1–2 天）
   ↓
③ ICP 备案（7–20 工作日，期间不可对外服务）★ 最长单项
   ↓
④ DNS 解析到 101.43.91.192
   ↓
⑤ 部署 SSL 证书 + Nginx 443 反向代理（TLS 1.2+）
   ↓
⑥ 根目录放置微信校验文件，确认 https://域名/xxx.txt 直接返回 200
   ↓
⑦ 小程序后台配置 4 类合法域名：request / uploadFile / downloadFile / socket
   ↓
⑧ 体验版真机验证（iOS 与 Android 各自验证证书链）
   ↓
⑨ 提交审核
```

**已知的六个坑（每条都踩一次就够痛）**

| # | 坑 | 规避 |
|---|----|------|
| 1 | 填了带端口或带路径的域名 | 只填根域名，不带端口、不带路径；非 443 端口必须用 Nginx 反代到 443 |
| 2 | 只配了 request 域名 | **uploadFile 是独立校验的**——我们上传走对象存储，必须单独配置对象存储域名，否则"能读不能传" |
| 3 | 证书链不完整 | 安卓真机报错而开发者工具正常，多半是中间证书缺失 |
| 4 | 域名根目录有跳转逻辑 | 微信校验文件必须能直接 200 返回文本，不能被 301/302 拦走 |
| 5 | 备案主体与小程序主体不一致 | 企业小程序不能用个人备案域名，主体需一致 |
| 6 | 域名含下划线 | 微信不允许，注册时就避开 |

**开发期如何并行（不必等备案）**

| 场景 | 做法 | 限制 |
|------|------|------|
| 开发者工具联调 | 勾选"不校验合法域名、web-view、TLS 版本及证书"，直连 `http://101.43.91.192:端口` | 仅开发版/体验版生效，**真机预览不生效** |
| 真机联调 | 用 frp / ngrok 等内网穿透拿临时 HTTPS 域名，配到"合法域名"里 | 临时域名不稳定，仅用于阶段性联调 |
| 对象存储直传 | 先用对象存储服务商提供的默认域名做开发期配置 | 上线前切到自有域名，避免依赖第三方默认域名的可用性 |
| 小程序提审 | **必须等域名 + 备案 + 证书全部就绪** | 无替代方案 |

> 规则：阻塞项未就绪不得承诺对应阶段的上线时间。

### 附录 C：原型思路（关键页面）

**Web 记录编辑页**

```
布局：左侧动作列表（窄） | 中间当前动作与组表格 | 右侧媒体与备注（可折叠）
顶部：计时器 / 日期 / 结束训练（主按钮）
组行：序号 | 重量(kg) | 次数 | RPE ▾ | 类型 ▾ | ✓
交互：
- 新增行自动预填上次数据，聚焦"次数"（重量多数情况不变）
- 回车 = 保存该组并新增下一行
- 勾选完成行的视觉弱化，未完成行高亮
- 媒体区拖拽上传，显示进度与"处理中"
- 断网：顶部黄条"离线记录中，联网自动同步"
```

**小程序训练中页**

```
顶部：当前动作名 + 组数进度（2/4）
中部：大号数字输入（重量 / 次数并排），下方"上次：60×8"
底部吸底：完成本组（主）/ 加一组（次）/ 计时器悬浮球
交互：
- 数字键盘直出，无多余字段；RPE 折叠在"更多"
- 完成一组触发休息计时（可跳过）
- 训练结束需二次确认（"结束并保存？"）
```

**Web 编辑页（块编辑器）**

```
顶部：标题输入（大字号）| 保存状态 | 预览 | 发布
左侧：+ 块菜单（斜杠命令同源）
右侧：媒体库 / 嵌入卡片 / 版本历史
块交互：hover 出现拖拽手柄与 +；嵌入卡显示"数据来源"角标
发布面板：可见性（仅自己/链接可见/公开）+ 封面 + 摘要 + 是否允许收录
```

**打卡页（小程序）**

```
顶部：连续 N 天 + 本周目标进度条
中部：月历（已打卡实心/补记描边/今日高亮）
底部：今日状态卡（有记录→"自动打卡完成"；无记录→"补记训练"）
次要：徽章墙入口
```

### 附录 E：关键假设（可推翻，需评审确认）

1. 用户愿意为"记录 + 内容"在同一工具内完成而迁移，迁移成本由"导入/快速补记"降低。
2. 训练场景以健身房力量训练为主，视频以 1–3 分钟片段为主（据此设定视频限制）。
3. 一期不做付费，存储成本由自有预算承担。**v1.1 修订：配额放宽至 50GB 后，成本假设从"配额从严即可控"变为"必须靠护栏把人均压到 6GB 以内"，此假设需财务确认月度上限后才成立。**
4. 小程序承担 60% 以上记录行为，Web 承担 70% 以上长文写作（估算，需埋点验证）。
5. **v1.1 修订**：公开页 + 分享卡 + 「敬请期待」占位点击率，三者叠加可验证社区需求，无需一期就建 feed。若占位点击率显著偏低，说明社区优先级应后移而非提前。
6. 视频水印为"品牌露出"而非"防盗版"手段，故可为用户关闭（D-10）；若后续出现批量搬运，需重新评估强制水印。
